      Finding: query-level readonly is not a security boundary in ClickHouse

      A later SETTINGS clause wins, so a model that appends its own settings undoes the guard. Reproduced on embedded ClickHouse (chDB).

      SELECT count() FROM agent_events SETTINGS readonly = 1, readonly = 0   -- runs
SELECT * FROM file('/etc/passwd', 'LineAsString') SETTINGS readonly = 2 -- reads a local file
      L1Validate: one SELECT, no comments, no SETTINGS, no table functions, allowlisted tables. Runs here in your browser, ported from hunt.validate_sql.
      L2Wrap in an outer SELECT with a row limit.
      L3Execute as a database user whose profile pins readonly = 1 CONST.

      What it runs on

      Swappable by design: storage and the LLM each sit behind one module.

      What is real and what is not

      • Telemetry and the attack chain are synthetic. The attack is scripted so the demo is reproducible.
      • Detection timings and counts come from a real ClickHouse run over every row.
      • Containment writes controls to a table; a simulator enforces them. Nothing touches real infrastructure.
